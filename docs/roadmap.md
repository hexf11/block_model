## 哪些特征现在就该写，哪些要等

有两类，把它们混为一谈会在两个方向上都浪费时间。

**结构性的 —— 现在就能写，不需要数据。** 5 分钟 UP/DOWN 市场本质是一个障碍穿越问题，所以 T-110s 时刻的主导信号是可以解析推导出来的：

```
normalized_distance = (P_now - P_open) / (σ · √t_remaining)
```

价格距开盘价有多远，再用剩余时间的波动率去做缩放。这就是 Black-Scholes 的 d2 项。不需要任何数据就能确定它该进模型，因为这是从收益结构本身推出来的，而不是从观测里得来的。剩余时间、已实现波动率（反正做缩放也需要它）、以及 TWAP-30 自身的动量，同理。

**经验性的 —— 必须等数据。** 窗口长度（10 秒？30 秒？60 秒？）。盘口深度在交易流之外是否还能带来增量信息。Binance 是否领先 Coinbase，领先多少。交易所数据究竟能不能打得过只用 TWAP 的基线。这些都没有站得住脚的先验。现在猜，等于以后还要再猜一遍。

## 为什么用 ONNX 作为特征契约

看起来很诱人的做法 —— 在 Python 里探索，再把胜出的特征移植到 Rust —— 恰恰是训练/服务偏差的来源。同一个特征的两份实现一定会漂移，而漂移是看不见的：两边单独看都像是对的。

正确做法是：Rust 为两条路径计算完整的特征超集。训练读取它、做筛选、然后导出。导出的 ONNX 文件的输入名称此时*就是*契约 —— 推理端读这些名字，从训练时看到的同一个超集里取出对应子集。

这里刻意不用一个列出所选特征的配置文件。配置文件可能和它本该描述的模型不一致，而 ONNX 计算图不可能跟自己不一致。

## 值得记住的设计决策

**生产环境全 Rust。** 最初的采集器是 Python 写的，也能跑，但一个 24/7、约 2500 msg/s 的守护进程需要单个二进制、可预测的内存占用、没有 GIL。Python 保留在 `research/` 里，那边生态确实更好，而延迟无关紧要。

**ClickHouse 里价格用 `String`。** 交易所给的十进制文本，原样保留。在边界上就解析成浮点，会在特征代码看到这个数字之前就把舍入烙进去。

**TWAP 用 `Decimal128(18)`，存放缩放后的整数。** Chainlink 的 `full_accuracy_value` 本身已经放大了 1e18。原样存储意味着不用做除法，也不存在精度问题。六位数的 BTC 价格乘上 1e18 超出 `u64`，所以 128 位宽度是真的必需，不是防御性设计。

**JSONL 的不对称性。** RTDS 永远镜像，因为它无法重放；交易所只在插入失败时才写，因为镜像它们要花约 43 GB/天。这个策略是从可重放性推出来的，而不只是看数据量。

**基于抓取帧的 parser 测试。** 这里真正要命的 bug 是语义层面的，不是语法层面的 —— taker 方向搞反、或者快照标志处理错，会长期产出看起来合情合理的数字。每一个这样的场景都有一个测试，并在测试名里写明后果。
